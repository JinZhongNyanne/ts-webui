# 功能路线图：补齐 TeamSpeak 3 / TeamSpeak 6 客户端功能

目标：把原生 TS3 客户端和 TS6 客户端有、而 JinzTS 还没有的功能全部补上。
本文先说明现状，再把缺口分成 M0–M8 共九个里程碑。里程碑用 M 编号，
以免和 `docs/phase-*-remaining.md` 里那几期安全加固的 Phase 0–3 混淆。

规模估计：**S** ≈ 1 天以内，**M** ≈ 2–5 天，**L** ≈ 1–2 周，**XL** = 需要先调研，或者要改架构。

### 做了一半

- **悄悄话**：能收能发，但只有一份悄悄话列表；没有“按服务器组”和“新格式”目标；接收策略只有“全部接收 / 全部屏蔽”，没有“只收好友的”（要等 M6 的联系人）；手机上没有按住说悄悄话的入口。
- **Speex / CELT 频道**：两个方向的语音都被丢掉，Web 用户在这类频道里听不到也说不了。
- **权限**：只有只读的权限概览，不能编辑（权限编辑器按决定推迟，见 M4）。
- **虚拟服务器设置**：只开放 14 个日常字段；密码、端口、反 flood、上传下载配额仍要用原生客户端改。
- **媒体播放**：hub 的媒体链接也接受音频文件，但页面只给视频（mp4 / m4v / webm / ogv）做了播放器，音频文件仍是下载卡片；文件浏览器里的图片和视频也不能直接打开查看。
- **TS6 服务器**：能识别出来（`detectFlavor`），但没有做适配，也没有测过。

### 协议库能力（决定了哪些功能实现起来便宜）

`@honeybbq/teamspeak-client` 0.2.x 提供了这些接口：

- `execCommandWithResponse(cmd)`：可以发送任意客户端命令，并拿到返回结果。**所以管理类功能都不需要改协议库**，只要在 hub 里加命令封装和 zod schema。
- `fileTransferInitUpload/Download` 和 `uploadFileData/downloadFileData`：文件传输已经有了。`ftinitdownload` 带 `seekpos`，所以可以从文件中间开始读（媒体链接就是靠它）。
- `sendVoice(data, codec)` 没有悄悄话目标参数，但公开类型上的 `client.handler.sendPacket` 可以直接发 `VoiceWhisper` 包，实测服务器只转给目标，**发送不需要 fork**。接收时库把普通语音和悄悄话合并成一个事件并丢掉包类型，所以用 `patch-package` 打了一行补丁（`patches/@honeybbq+teamspeak-client+0.2.3.patch`）把类型留下来；Docker 构建里也会应用。

### M2 遗留

- 封禁：`banclient` 会同时封 UID 和 IP，而所有 Web 用户共用 hub 的 IP，所以封禁对话框默认只按 UID 封（`banadd uid=`），“UID 和 IP”选项带警告。TS3 没有 `banedit`，编辑是先加新封禁再删旧的。
- 拖动移动用户和频道只支持鼠标；手机上用菜单里的“移动到…”。频道拖动在手机上还没有替代入口。
- 离线消息：服务器不会推送新消息通知。除了每次连接时查一次未读数，离开标签页（隐藏或失去焦点）至少 5 分钟后回来时会再查一次，每个会话最多 10 分钟一次（走 hub 的全局命令额度），未读数变多时在服务器聊天里提示。

已解决（分支 `fix/m2-leftovers`）：

- 被封禁时有自己的音效和桌面通知（“被服务器封禁”，写明是谁封的和理由），设置里的通知面板可以单独开关。
- 服务器组 / 频道组的增删改：在真实 TS3 服务器上确认，任何一个组被添加、改名或删除后，服务器都会给每个客户端重发完整的 `notifyservergrouplist` / `notifychannelgrouplist`；hub 现在用每次重发的完整列表替换旧列表，删掉的组不用重连就会消失。
- 给已有的组再加一次（2561 duplicate entry）或移除没有的组（2563 empty result set）：服务器组对话框当作“已经是 / 已经不是成员”，勾选状态按服务器的回答显示；2561 在其他地方显示“已经在这个组里了”。

### M3 文件传输

hub 负责和 TS 文件端口（默认 30033）之间的 TCP 传输；浏览器与 hub 之间用 HTTP 流传输（上传用 `PUT`，下载用 `GET`，认证沿用 asset token 和 `x-session-id`），**文件不在 hub 里整份缓存**。

| 项             | 说明                                                                                        | 规模 |
| -------------- | ------------------------------------------------------------------------------------------- | ---- |
| 频道文件浏览器 | `ftgetfilelist`、`ftgetfileinfo`；每个频道的文件树，频道有密码时要输入                      | M    |
| 上传 / 下载    | 进度、取消、队列；大小上限按 `i_ft_*` 权限和 hub 配置里较小的那个                           | L    |
| 文件管理       | `ftcreatedir`、`ftdeletefile`、`ftrenamefile`                                               | S    |
| 头像上传       | 裁剪和压缩后上传到 `/avatar_<base64uid>`，再用 `clientupdate client_flag_avatar=<md5>` 更新 | M    |
| 图标上传与管理 | 上传到频道 0 的 `/icon_<crc32>`，然后通过 `i_icon_id` 权限设置到组或频道上                  | M    |
| 聊天里发文件   | 仿照 TS5/TS6：文件上传到当前频道，聊天里发一个带下载链接的消息（原生客户端能看到链接）      | M    |

**✅ 已完成**（分支 `integrate/m3`，包括表情；视频边下边播在本期补上）。遗留：文件浏览器不能在界面里跨频道移动文件；别人改了文件不会自动刷新；表情分组不能排序、不能跨范围复制；音频文件没有播放器。

安全上要注意：限制上传的大小和速率；普通下载一律设 `Content-Disposition: attachment` 并加上 `nosniff`，不能让服务器上的 HTML 文件在 hub 的源下直接打开。唯一的例外是下面的媒体链接：只对文件名是视频 / 音频的文件内联返回，类型按文件名查白名单，从不信服务器说的。

**传输核心 ✅**（分支 `feat/m3-transfer-core`）：后面几项（文件浏览器、头像 / 图标上传、聊天发文件）都用它。

- hub：`POST /api/files/download-ticket`（`x-session-id`，JSON `{cid, path, cpw?}`）先在 TS 上发起下载，返回一次性链接 `/api/files/download/<ticket>`（8 秒内有效、只能用一次、频道密码不进 URL；TS 服务器约 10 秒不连文件端口就作废）；`PUT /api/files/upload?cid=&path=&overwrite=1`（`x-session-id`、`x-ts-channel-password` 百分号编码、`Content-Length`）把请求体原样流到文件端口。都不在 hub 里缓存整个文件，50 / 250 MB 实测内存不涨；取消的上传会被 `ftdeletefile` 删掉（TS 会留下半截文件）。传输的 init 命令走 hub 全局的 `ts.cmd` 配额（server-guard），flood 时拒绝。
- 限额：`HUB_FT_MAX_UPLOAD_BYTES`（默认 100 MB，和 `i_ft_quota_mb_upload_per_client` 取小）、`HUB_FT_MAX_TRANSFERS_PER_SESSION`（3）、`HUB_FT_RATE_PER_MIN`（30），`hello.features.files` 会告诉页面。
- `ts.cmd` 新增只读的 `ftgetfilelist`、`ftgetfileinfo`；频道密码和 `clientmove` 一样要 SHA-1（明文会被拒 781），Server Admin 有 `b_ft_ignore_password`，密码错也能进。
- 页面：`stores/transfers.ts`（`uploadFile` / `downloadFile` / `cancel` / `waitFor` / `listFiles` / `fileInfo`，最多同时 2 个），`files/` 里是纯逻辑，`components/files/TransferList.vue` 挂在文件浏览器窗口底部。聊天里的文件链接应该存 `(cid, path)`，点的时候再调 `downloadFile` 换一次性链接。

**文件浏览器 ✅**（分支 `feat/m3-file-browser`）：

- 顶部窗口栏的“文件”窗口（和应用 / 视频 / 音效板在同一组标签里），频道右键“浏览文件…”直接打开那个频道；手机上是菜单里的“文件”和同一个右键菜单，打开底部弹层。选频道（默认自己所在的频道）、面包屑、按名称 / 大小 / 时间排序（文件夹总在前面）、双击进文件夹或下载、多选（Ctrl / Shift / 勾选框）。频道有密码时在窗口里输入，本次连接内记住。
- 上传：按钮或把文件拖到列表上（可多个），先重新列一次目录，同名文件问一次“替换 / 跳过”；服务器返回 2050 时（别人刚传了同名文件）再问。底部是可折叠的传输列表，每个上传完成都会刷新目录。
- `ts.cmd` 新增 `ftcreatedir`、`ftrenamefile`（同频道改名 / 移动，也支持 `tcid` 跨频道）、`ftdeletefile`（一次最多 100 个路径）。在 TS3 3.13 上实测（`scripts/verify-m3-file-browser.mjs`）：这三个命令**不会通知任何人**（包括自己），所以做完都要重新列目录，别人要刷新才看得到；文件夹已存在 2050、父目录不存在 2052；**改名到已有的名字会直接覆盖那个文件**（不报 2050），所以页面先按列表检查；删除时按顺序处理，遇到第一个不存在的路径（2054）就停，前面的已删；`tcpw` 和 `cpw` 一样要 SHA-1。缺权限时点名 `i_ft_needed_directory_create_power`、`i_ft_needed_file_rename_power`、`i_ft_needed_file_delete_power`、`i_ft_needed_file_upload_power`。
- 按钮按客户端自己的 power 显示（`i_ft_file_upload_power`、`i_ft_directory_create_power`、`i_ft_file_rename_power`、`i_ft_file_delete_power`、`i_ft_file_browse_power`、`i_ft_file_download_power`）：服务器只报告拥有的，游客读不到就照样显示，由服务器拒绝并说明缺哪个权限。
- 遗留：跨频道移动只有命令，界面里没有；别人改了文件不会自动刷新（服务器不通知）。

**聊天里发文件 ✅**（分支 `feat/m3-chat-files`）：输入框旁的 📎、拖进聊天、粘贴截图都可以。文件传到频道里（频道聊天就是那个频道；私聊和服务器聊天传到自己所在的频道，界面上会说明），按类型分进 `/imgs` 或 `/files`（见下面的“聊天分文件夹”；最初是频道根目录），重名时加 “ (2)”，列不出目录时在名字后加时间；上传中在输入框上方显示进度，可以取消。发出去的消息和 TS3 客户端从文件浏览器拖进聊天时一样：`[URL=ts3file://<host>?port=<port>&channel=<cid>&path=<目录>&filename=<名字>&isDir=0&size=<字节>&fileDateTime=<unix 秒>]名字[/URL]`（只在必要处百分号编码，非 ASCII 原样保留；控制在 1024 字符内）。收到的 `ts3file://` 链接显示成文件卡片（名字取自链接本身，不取标签），从不变成 href；“下载”每次现换一次性链接，频道有密码时先问；图片点“预览”后才经 hub 下载并用 `blob:` 显示。TS5/TS6 在自家服务器上发文件走 myTeamSpeak 云端，和这里不互通。代码在 `apps/web/src/chat/files/`。

**头像上传、图标上传与管理 ✅**（分支 `feat/m3-avatar-icons`）。在 TS3 3.13 上实测的规则写在 `packages/protocol/src/ts-internal-files.ts`：

- 头像：设置 → 我的资料 →“TeamSpeak 头像”，裁成正方形（最大 300×300，PNG，超出 `i_client_max_avatar_filesize` 就改 JPEG 逐级压缩），上传到频道 0 的 `/avatar_<UID 字节的 a–p 十六进制>`，再 `clientupdate client_flag_avatar=<文件 md5 小写十六进制>`。删除先清空 flag，再 `ftdeletefile name=/avatar_<base64 UID>`（这个命令要 base64 形式，a–p 形式会报 1540；而且连删自己的都要 `b_client_avatar_delete_other`，没有就只清 flag）。服务器不检查头像文件名是谁的（游客能覆盖别人的头像），所以 hub 只允许往频道 0 上传自己的头像和 `icon_<id>`。
- 图标：服务器右键 → 管理 →“图标…”（`b_icon_manage`），列表是频道 0 的 `/icons`；不大于 16×16 的原样上传（id = 文件的 CRC-32，和原生客户端一致），更大的缩成 16×16 PNG；上限 `i_max_icon_filesize`（Server Admin 8192 字节）。设置图标用 `servergroupaddperm` / `channelgroupaddperm` / `channeladdperm` / `clientaddperm` 的 `i_icon_id`（都只放行这一个权限），入口在服务器组 / 频道组对话框每行末尾、频道和用户的右键菜单“设置图标…”。超过 2^31 的 id 按 int32 发送；服务器在 `notifychanneledited` 里把它写成符号扩展的 64 位数，hub 现在统一取低 32 位。改完服务器会推 `notifyservergrouplist` / `notifychannelgrouplist`（整张表）、`notifychanneledited channel_icon_id`、`notifyclientupdated client_icon_id`，所有人即时更新。

**M3 评审修复 ✅**（分支 `fix/m3-web-review`）：

- 传输名额：下载的名额在**发链接时**就占住，直到流结束或链接过期未用才还，所以 GET 再也不会被拒（浏览器不会把一份 JSON 错误存成文件；真要失败也只回一小段 `text/plain`）。下载最多占 `HUB_FT_MAX_TRANSFERS_PER_SESSION - 1` 个名额，留一个给上传（头像、聊天发文件）。答 `ft.busy` 不再消耗每分钟的 init 配额。
- 页面队列：拿到 `busy` / `rate_limited` 的传输不再算失败，而是排回队列、按 1/2/4/8 秒退避重试（`transfers.state.waiting`）。聊天里的图片预览也走同一个队列（`transfers.fetchFile`）。
- 传输有了来源（`origin`）：文件浏览器的列表只显示自己发起的；头像 / 图标这类小文件插队、不占页面的并发上限，两个对话框都能取消；完成的传输最多保留 50 条。
- 频道密码只有一处（`ts/channel-passwords.ts`），而且**只在服务器接受之后**才记：目录列出成功、移动成功、下载链接发出来了。连接时的 `defaultChannelPassword` 也记下来，聊天卡片里输对的密码文件浏览器也能用；服务器拒绝已记住的密码就忘掉它。
- 其它：上传重试用的是开始时的频道 / 目录 / 密码（不是当下看着的那个），“文件已存在”按错误码 2050 判断而不是比对译文；“文件”窗口和菜单跟着 `features.files` 显示；上传完发聊天消息前先确认还在那个频道，否则不发并说明文件在哪；预览缓存按字节上限（50 MB）并在重连时清掉；指向**别的服务器**的 `ts3file://` 卡片不给下载按钮（只在真分不清时放行，比如一边是 IP 一边是域名，或本地回环地址）。

**聊天分文件夹 ✅**（分支 `feat/stickers`）：聊天里传的文件不再堆在频道根目录。能预览的位图（png / jpeg / gif / webp / bmp / avif）进 `/imgs`，其余进 `/files`，第一次用到时才 `ftcreatedir`，服务器答 2050（已存在）也算成功。有上传权限但没有 `i_ft_needed_directory_create_power` 的人退回根目录，界面上不提这件事——建不了文件夹不是发送者要操心的问题。重名加 “ (2)” 的逻辑现在作用在那个文件夹里，`ts3file://` 链接里的 `path=` 也跟着写真实目录，原生客户端和文件浏览器都照常。纯逻辑在 `apps/web/src/chat/files/folders.ts`。

**表情（贴纸）✅**（分支 `feat/stickers`）：输入框旁的 😀，桌面和手机上都是同一个组件（`components/chat/StickerPicker.vue`），点一下就发到当前对话。

- 两个范围。**共享**和音效板、应用列表一样是整个 hub 的：连上的人都能看、都能加、都能改名和删；**个人**按 TeamSpeak 身份 UID 存，只有本人能读写，换设备用同一身份登录还在。范围从会话里的身份取，请求里从来不说“谁的”，所以拿到别人的 id 也动不了别人的（测试里验证过）。改动用 `stickers.updated` 推：共享的推给所有连上的会话，个人的只推给该身份的会话（同一个人开两个标签页也同步）。
- 每个范围里可以自己建**分组**（pack），一层，不能再往里套；没进分组的落在隐含的“未分组”里。删分组时问一句：把里面的表情挪到“未分组”，还是连着一起删。
- **按内容去重**：图片按 SHA-256 存成 `blobs/<hash>.<ext>`，一个 hub 只存一份；引用数就是“有多少条目写着这个 hash”，不另外记一个数，所以永远不会对不上。再传一张已经有的图片只多一条目录项，删掉最后一条引用才删文件。`/api/sticker-file/<hash>` 带 asset token 读，URL 就是内容，所以可以长期缓存（`immutable`），配 `nosniff`。
- **发送**走已有的聊天发文件那套：图片按 hash 命名成 `sticker_<hash 前 12 位>.<ext>` 传进频道的 `/imgs`，再发普通的 `[URL=ts3file://…]` 消息，原生 TS3 客户端也看得到。同一个频道里第二次发同一张表情**不会再传一遍**：先列目录，名字在就只发消息；两个人同时发时输的那个会收到服务器的 2050（已存在），那也正是想要的结果，一样算命中。共享出口只有 hub 一个 IP，所以省下的这次上传是实打实的。
- 上限：共享 500 张、个人每人 200 张、每个范围 50 个分组，单张 512 KB，边长 1024 像素（只有页面量得出来，hub 靠字节上限兜底），名字 1–32 字符，每会话每分钟 40 次写。类型只认 png / jpeg / gif / webp，**按文件头判断**，不信浏览器说的类型；SVG 不收（那是能带脚本的文档）。
- 遗留：分组不能拖动排序，也没有跨范围复制（“把这张共享的存进我自己的”要重新上传一次，去重会让它不占额外空间）；表情没有标签或搜索索引，只能按名字搜；没有导入 / 导出整包；共享范围里谁都能删别人加的（和音效板、应用列表一致，hub 是熟人用的）；`/imgs` 里的表情文件不会自动清理，和别的聊天文件一样留在频道里。

**图片查看器 ✅**（上一轮，`integrate/m3`）：点聊天里的图片或表情，在桌面上方打开查看器：适应窗口、100%、按钮和滚轮缩放（以指针为中心）、拖动平移、双击在适应和原始大小之间切换；手机上单指平移、双指捏合，双击切换。只显示消息已经加载过的地址，不经 hub 再取一次，所以外链图片的“点击才加载”依然有效。代码在 `apps/web/src/components/viewer/`。

**聊天里的视频 ✅**（上一轮做播放器，本期做流式）：mp4 / m4v / webm / ogv 显示第一帧和播放标记，点开是播放器（播放 / 暂停、进度、静音和音量，空格、方向键、M、Esc）；不自动播放，语音引擎在跑时打开默认静音。本期加了**媒体链接**：`POST /api/files/media-ticket` 换一个只对应一个文件、只属于一个浏览器会话和那条 TeamSpeak 连接的链接，十分钟内可以反复用，同一文件再要一次就替换旧的；每个 GET 是一次 `ftinitdownload seekpos=<起点>`，回 206 和 `Content-Range`（TS 不能提前结束，所以都是开放区间）。每个会话每分钟 12 次打开（`HUB_FT_MEDIA_OPENS_PER_MIN`），每个链接占一个下载名额，同一链接的新请求接手旧请求的名额并切断旧流。hub 不支持时退回整份下载，上限 32 MiB。第一帧预览把画面拷成 `data:` 图片后就放开链接，不和播放器抢同一条流。

### PWA、存储和布局的其它改动

- **可安装的 PWA**：manifest、图标和 service worker；Chrome、Edge、Android 会提示安装，iOS 可以加到主屏幕。worker 只缓存带 hash 的 `/assets/*`，页面、API、websocket、文件链接都直接放行；worker 自己的响应有单独的 CSP。本期加了：缓存按构建 id 命名，激活新 worker 时删掉其它构建的缓存；已安装的应用在图标上显示未读数（`navigator.setAppBadge`）。图标还是占位的字母图案。
- **上传的文件移进 `blobs/`**：音效、头像、应用图标原来和各自的 JSON 索引放在同一个目录，现在都在 `blobs/` 子目录里（表情一直是这样）。每个 store 启动时把旧位置的文件搬过去，只搬自己会写的名字，不覆盖、不删除；但**回滚镜像不会搬回来**，升级前先给 `HUB_DATA_DIR` 做快照。另外，索引读不出来（不是“不存在”）时不再按空索引清理 blobs，也不覆盖那份索引。
- **弹出框不再被窗口裁掉**：表情选择器和音效板的音量弹出框挂到 body 上，按视口定位，窗口移动时跟着走；手机上跟随 visual viewport，键盘弹出时不被挡住。
- **手机布局**：刘海和横屏两侧的安全区、所有触控目标至少 44px、弹层用 dvh；查看器的捏合、双击、拖动在手机上修好了。

## 3. 建议顺序

1. **M0**：先把命令通道、权限感知和测试环境建好，后面每一项才能各自做成一个小 PR。
2. **M1**：改动小、见效快，可以和 M0 后半段并行。
3. **M2 → M3 → M4**：管理员最需要的功能。权限编辑器（XL）单独做一个 PR 系列。（到 2026-09-22，M2、M3 完成，M4 只差权限编辑器。）
4. **M5**：先给协议库打补丁，确认悄悄话能发出去，再做界面。（悄悄话已完成；Speex / CELT、立体声、录音、3D 语音、音质设置还没动。）
5. **M8 的 TS6 测试**：可以一开始就在 CI 里并行跑。其它 TS6 功能在 M1–M5 之后做。
6. **M6**：多服务器涉及架构改动，放在功能都稳定之后。
7. **M7**：按需做。

每个里程碑结束时，照现有的 `docs/phase-*-remaining.md` 惯例写一份“还剩什么”，
PR 里附上端到端验证（两个客户端加一个 serveradmin）。

## 4. 明确不做

- ServerQuery 相关：快照、`serverprocessstop`、实例管理（客户端协议里没有这些）。
- 需要 myTeamSpeak 私有接口的功能：直接通话、社区、全局聊天、云端书签同步。
- 原生插件 SDK 兼容。
